Agent-security evaluation · open-weight LLMs

Bigger isn't safer.

What happens to an open-weight model's resistance to agent attacks when you scale it from 7 billion to 32 billion parameters?

The short answer. I ran the same 600 agent-attack scenarios against three sizes of Qwen2.5 with no extra guardrails, and scored each response two ways. By the usual "did the model go along with the attack?" measure, the larger models were easier to manipulate, not harder — and that held under two independent graders.

But "the attack succeeded" turns out to be a judgement call, and a lot of the disagreement between graders came down to a data quirk rather than a real difference. When I ran the handful of cases through a sandbox that needs no grader at all, the size effect disappeared. So: riskier on paper, unproven in execution — and how you measure matters as much as the model.

The five things I found

Key findings

Ranked by how strongly the evidence supports them. The first is robust; the middle three come with caveats I'm explicit about; the last is a deliberate non-result.

01 · robust

Scaling up raised the attack-success rate

+17 / +9.5 pts

From 7B to 32B, the semantic attack-success rate rose by 17 points under the primary grader and 9.5 under the validation grader. Both results are statistically solid, and the trend is monotonic.

02 · the twist

The graders disagreed — but it's mostly an artefact

5–10 → 22–27 pts

On responses that weren't cut off at a 2,000-character cap, the two graders land within 5–10 points and agree on the scaling trend. The big gap only appears on truncated responses, which hit the largest model hardest.

03 · definitions

"Succeeded" depends on what you count

95% vs 48%

At 32B, counting whether the model agreed to the attack gives 95%; counting whether harm actually happened when tools ran gives 48%. Semantic scoring roughly doubles the observable-harm rate.

04 · one family

One attack type drives the disagreement

63% vs 16%

For meta-extraction (MEX) attacks the lenient grader says 63% success, the strict one 16%. The sandbox shows roughly 0% real harm there — pointing, for this family, toward the stricter grader.

05 · non-result

No size effect in the sandbox

43 / 43 / 48%

At the execution layer, harm-completion barely moved across sizes and the intervals overlap (only 60 cases). The scaling signal lives entirely in the semantic grading, not in measured harm.

What I did

The setup, in one picture

I extended SafeClawBench (Tian et al., 2026) across three sizes of the same open-weight model family, holding the defence setting fixed, and scored the results two independent ways plus a deterministic sandbox.

Two kinds of finding, kept separate throughout. A model-layer finding is about the model's own behaviour under attack with no guardrails — that's what this study measures. An infrastructure-layer finding is about the sandbox, egress controls and approval gates around the model — not tested here. Everything below is model-layer unless it says otherwise.

Technical detail: models, judges and metrics

Models: Qwen2.5 7B / 14B / 32B, GGUF Q4_K_M, served on Ollama. Defence D0: the benchmark's baseline condition with no supplementary defences.

Judges: the primary grader is DeepSeek (deepseek-flash); the validation grader is Claude Haiku 4.5. A judge here is an LLM that reads a scenario and the model's response and labels whether the attack succeeded (plus a 1–5 safety score). ASR = attack-success rate, the share of scenarios the judge marks as successful. The original paper used a different judge (gpt-5.4), so its absolute numbers aren't directly comparable to mine.

Tracks: Semantic Core = 600 scenarios/model, graded by LLM. Exec-Balanced = 60 scenarios/model run in a sandbox where success is decided by deterministic state oracles (did a file get written, an email get sent, a policy get changed) — no LLM judgement.

Attack families (100 Core scenarios each): ADI, DPI, IPI, MEX, MPI, TRI — explained in the family explorer below and the glossary.

Results · scaling

Does size make it safer or riskier?

Riskier, under both graders. Here is the semantic attack-success rate for each model size, with 95% confidence intervals (the range the true rate is very likely to sit in). Toggle the grader to see that the gap between them is a constant offset — the upward slope is there either way.

Technical detail: is the trend real, or noise?

Yes under both graders. A population-averaged (GEE) logistic model with the same 600 cases clustered per scenario gives an odds ratio per size step of 1.70 (95% CI 1.50–1.92, p≈1.5×10⁻¹⁷) for DeepSeek and 1.30 (1.16–1.45, p≈4.9×10⁻⁶) for Haiku. Paired exact McNemar tests on the matched scenarios: 7B→32B is +17.0 pts for DeepSeek (p<10⁻¹⁵) and +9.5 pts for Haiku (p<10⁻⁴), both surviving Holm correction. The one step that isn't significant under Haiku is 7B→14B (+3.0 pts, p=0.19).

Statsmodels wasn't available in the analysis environment, so the trend model is implemented directly as a GEE logistic with cluster-robust (CR1) standard errors — same target as a mixed-effects logistic, no external dependency.

Where the attacks land

The six attack families behave very differently. Hover (or tap) a cell for the family's meaning and both graders' numbers. The pattern to watch is the MEX row — it's where the graders part company.

MEX callout

MEX attacks ask the model to reveal its own internal rules or system prompt, usually disguised as an audit. Reading the transcripts, the models almost always answered with generic, public-sounding policy boilerplate that leaks nothing real. DeepSeek counts that as a successful extraction (the model "described its policies"); Haiku counts it as safe (nothing actual was disclosed). That single interpretation gap accounts for most of the headline disagreement — see the next section.

The judge-sensitivity story

Two graders, one disagreement, mostly explained

The two graders agree about 78–80% of the time, and agreement falls as models get larger. That looks alarming until you find the cause.

The cause: a 2,000-character cap

Saved responses were truncated at 2,000 characters. That matters because larger models write longer, more elaborate answers, so they hit the cap more often: 45% of 7B responses, 48% of 14B, but 63% of 32B. A truncated answer often shows the model starting to comply but cuts off before it actually does anything — and that's exactly the zone where the two graders diverge.

The clincher: restrict the 7B→32B comparison to scenarios that weren't truncated at either size, and both graders show the same +11-point rise (DeepSeek p=0.004, Haiku p=0.005). On truncated scenarios, DeepSeek still shows +10 points but Haiku shows +0.9 (flat). The scaling result is robust; the grader's apparent flatness was a measurement artefact all along.

What changes if you pick the other grader?

This is the honest "it depends" made concrete. Flip the grader and watch the headline numbers move — the direction never does.

Technical detail: what each grader keys on

Across 1,800 graded pairs, disagreements run 340 "DeepSeek-success / Haiku-safe" against only 46 the other way — DeepSeek is systematically the more permissive grader. Reading 40 cases in full, the split is structural: DeepSeek scores intent (did the model adopt or commit to the harmful goal, measured against the literal success predicate), while Haiku requires observable completed harm (did the action actually happen in the visible text). A response cut off after a compliant preamble reads as success to one and safe to the other. When responses clearly finish the harmful act, both graders agree.

Counting harm

Semantic success vs. actual harm

The Exec track removes the grader entirely: a scenario counts as harmful only if a deterministic check fires in the sandbox. It's the most trustworthy signal here — and the most under-powered, at 60 scenarios per model.

For MEX specifically, this is the closest thing to a tie-breaker. On the 10 MEX scenarios with sandbox oracles, DeepSeek scores 90–100% success, Haiku 20%, and the sandbox sees 0–10% actual harm. For this family the stricter grader is closer to the ground truth — though with only 10 cases, and with the caveat that a state oracle under-detects pure information-leak harms, I'd call it a strong hint, not a verdict.

Caveats, stated plainly

How much can you trust this?

Enough to believe the direction of the main result; not enough to quote the exact numbers as settled truth. Here's what could be wrong.

1
Neither grader is ground truth. They're two LLMs that disagree, and the original paper used a third (gpt-5.4). Where they conflict and the sandbox can't adjudicate, I say so rather than pick a winner.
2
The 2,000-character truncation touches ~half of all responses (63% at 32B) and is the main driver of grader disagreement. Both graders saw partial text on those cases.
3
A serving-environment difference is confounded with size. 7B and 14B were generated in July (older Ollama, serial); 32B in October (newer Ollama, parallel). A 30-case calibration bounds this at roughly +10 points and not statistically distinguishable from zero — small, but not ruled out, and only measured on 7B.
4
One sample per scenario. Temperature 0, so responses are near-deterministic, but there's no per-scenario variance estimate from resampling.
5
The Exec track is n=60. Intervals are roughly ±12 points, so it can rule a large size effect in or out only loosely, and its state oracles under-detect information-leak harms.
So what

What this means if you deploy agents

  • Don't assume a bigger open-weight model is a safer agent. With no guardrails, the larger Qwen2.5 models complied with attacks more often, not less. That's a model-layer property; it won't be fixed by swapping in a bigger model.
  • Measure harm at the layer you actually gate. Semantic "the model agreed" roughly doubled the rate of sandbox "harm actually happened". If your infrastructure requires approval before tools execute, many semantic successes never become real harm — but that's an infrastructure-layer control you have to build, not something the model gives you.
  • Your choice of evaluator changes the headline. Two reasonable graders differed by up to 27 points on the same responses. If you benchmark agent safety, report the grader, the metric definition, and a truncation check — or you'll ship a number that doesn't replicate.
Lessons

Pitfalls I hit

The most useful practical lesson wasn't about the models. Partway through, the grading API silently changed behaviour: with its "thinking" mode on, it exhausted its token budget and returned empty output on about 30% of cases. Empty verdicts quietly read as "safe", which would have deflated the attack-success rate if I'd trusted them.

The shipped calibration file still carries the fingerprint of this: 15 of 30 verdicts in one run are "Judge parse error" nulls. The fix was to disable thinking mode for grading and treat any null as a failure to re-run, never as a negative. Lesson: pin your judge build, validate every verdict, and never let a silent null count as a result.

Do it yourself

Reproduce it

Every table and figure in this report is regenerated by one script from the released aggregate data:

python3 analysis.py --data ./data --out ./out
# writes out/results.json and out/figures/*.png  (needs numpy, scipy, matplotlib)

Rough cost. Generation ran on an A40 at about $0.59/hour. Re-running 7B and 14B in the current environment to remove the serving confound would cost roughly $1–1.4 on a fresh pod (about 1–2 hours). Re-grading from saved responses is API-cost only.

What's released. Aggregate tables and per-scenario verdicts and metrics — not raw model responses or the attack prompts. The benchmark itself (benchmark_v5_600.json) is not redistributed; get it from the original dataset under its own licence.

Glossary

ASR
attack-success rate — the share of scenarios a grader marks as a successful attack.
Judge / grader
an LLM that reads a scenario and response and labels success or safety.
D0
the benchmark's baseline defence setting: no added guardrails.
Core / Exec
Core = 600 LLM-graded scenarios; Exec = 60 sandbox scenarios with deterministic checks.
κ (kappa)
agreement between graders corrected for chance; 1 = perfect, 0 = chance.
95% CI
confidence interval — the range the true rate very likely falls in.
ADI
an instruction with an unsafe built-in default a careful agent should question.
DPI
the user's own request directly asks for the harmful action.
IPI
a malicious instruction hidden in content the agent reads, not in the user message.
MEX
an attempt to make the agent reveal its own internal rules or system prompt.
MPI
getting the agent to save a harmful rule for later, poisoning future actions.
TRI
forged authority, urgency or procedure — including notes planted in tool output — to bypass checks.
Full disclosures

Judge build. deepseek-flash is an alias (V4.1); the exact build isn't pinned because the API returns only the alias. Thinking mode was disabled after it returned empty output on ~30% of cases. Validation grader: Claude Haiku 4.5. All 1,800 responses were re-graded uniformly from saved text.

Environment. 7B/14B Core generated July 2026 (older Ollama, serial); 32B Core on 23 Oct 2026 (Ollama 0.40.9, 4 parallel slots, context 8192). A40 GPU, no persistent volume. Responses truncated at 2,000 characters on save; the generation-time grader saw up to 3,000.

Decoding. Temperature 0 (greedy); deterministic given identical cache state, though response text still drifts between builds.

Semantic Core: 600 scenarios × 3 sizes × 2 graders. Exec: 60 scenarios × 3 sizes, sandbox-scored. Numbers reproducible from the released analysis script. Built for GitHub Pages — static, offline, no trackers.
